## Tier 1 — Automated / programmatic checks (no humans, no recruitment, run continuously)

These cost nothing in evaluator time and can run from Week 1 onward as regression checks, not just in the dedicated evaluation weeks.

### 1. Coverage check
Does every job, trigger, and secret present in the IR actually appear somewhere in the generated documentation? Since you control the IR, this is a straightforward scan: for each IR field, check it's referenced in the output text. Gives you a hard completeness number, not just a subjective "felt complete" rating.

### 2. Diagram-structure check
Does the Mermaid graph's nodes and edges match the IR's job dependency graph exactly? Automatable via graph comparison (build the expected graph from the IR, parse the generated Mermaid, diff them). Validates Tool 2's "unified diagram" claim without needing a human to eyeball it.

### 3. Determinism / variance check
Run the same pipeline through the LLM layer multiple times (and at different temperature settings). Measure how much the natural-language output varies while the underlying facts stay fixed. Matters for your argument that this is a *trustworthy* dev tool, not just a fun demo.

### 4. Readability metrics
Flesch-Kincaid or similar, computed on the generated text. Not a replacement for human judgment on clarity (that's Hu et al.'s whole point, and still holds), but a free secondary signal that costs nothing to add.

**Recommendation: include all four.** They strengthen Methodology and Evaluation sections without touching evaluator recruitment.

## Tier 2 — Robustness / stress testing

### 5. Error injection
Deliberately break test pipelines — a dangling dependency, a malformed `if` condition, an undefined secret reference. Does the tool flag the problem, or silently produce plausible-but-wrong documentation? This is exactly the kind of stress test examiners want to see in a critical reflection, and it's a direct test of hallucination risk in the LLM layer.

**Recommendation: include.** Cheap to build (you already have working pipelines to mutate), and it's a strong, specific data point for the Reflection section.

---

## Tier 3 — Comparative / correctness methods (uses real repos, moderate setup cost)

### 6. Correctness check (already in original plan)
Trigger real pipelines on 4-5 real repos, compare GitHub's actual job/status output against what the tool documented. Validates the parsing + IR layer specifically.

### 7. Natural-pairs comparison (upgrade to "vs. human-written docs")
Instead of asking recruited people to write fresh documentation for the study, find repos that **already have** human-written pipeline documentation — READMEs, CONTRIBUTING.md, wiki pages describing the CI setup — and compare the tool's output against those directly.

This removes a recruitment dependency (nobody has to write anything new) and gives you documentation that's "real" — written for actual developers, not written for the purpose of your study. Directly satisfies the brief's "comparing... with documentation written by human developers" requirement.

**Recommendation: use this as the primary human-comparison method**, replacing "ask evaluators to write docs" with "find docs that already exist." Less recruitment risk, more authentic baseline.

## Tier 4 — Human judgment (the core method, needs recruitment lead time — start Week 5)

### 8. Blind three-way comparison (Tool 1)
Show evaluators three unlabeled outputs for the same pipeline, blind:
1. Plain structured text (Layer 3a, no LLM)
2. Full tool output (structured text → LLM-polished)
3. Naive baseline — raw YAML dumped straight into an LLM with an "explain this" prompt

This directly tests your architecture's central claim (Python-extraction-then-LLM beats "just ask an LLM to read the YAML") rather than just asserting it.

Rate each on: accuracy, clarity, completeness, usefulness (1-5). Also collect a **blind pairwise preference** ("which would you rather read?") alongside the Likert scores — preference judgments are more statistically robust than absolute ratings when your evaluator pool is small (6-8 people).

### 9. Task-based comprehension test (Tool 2)
Rather than only rating the unified doc, test whether it actually helps:
- Give evaluators a repo with multiple pipeline files
- Ask concrete questions: *"If I push to main, what runs?" "Which pipeline fires on a PR to the release branch?"*
- Split evaluators: half answer using only the tool's unified doc, half using only the raw YAML files
- Measure: answer accuracy, time taken, self-reported confidence

This tests comprehension outcomes, not just stated preference — a stronger claim for "this tool helps developers understand their CI setup."

**Recommendation: run both.** This is the load-bearing evaluation work — start evaluator recruitment in Week 5 as already planned, don't compress it into Week 6.

## Tier 5 — Qualitative depth (optional, cheap on person-count even if rich in output)

### 10. Think-aloud sessions
2-4 developers walk through the tool's output live while narrating their reactions, instead of only filling in a static form. Richer material for the Reflection section than survey numbers alone, and it's only 2-4 people — cheaper on total evaluator time than it sounds.

**Recommendation: include if Week 6 has slack after Tier 4 is done. Nice-to-have, not load-bearing.**

---

## Tier 6 — Stretch goals (high effort or dependent on others, explicit stretch only)

### 11. Real PR submission
Submit 1-2 generated docs as actual pull requests to open-source repos (the project brief explicitly flags this as a possibility). Whether maintainers accept, request changes, or reject is a genuinely novel data point — very few dissertations get external validation like this.

**Risk:** maintainers may not respond within your timeframe. This cannot be a load-bearing evaluation method — treat as something you *attempt* and report honestly on either way ("submitted, pending response" is still a legitimate thing to write up).

### 12. Practical/systems metrics
Generation time and API cost per pipeline. Relevant only if you want to argue the tool is practical to run inside a real CI process, not just academically interesting. Cheap to log, low priority to analyze deeply.

**Recommendation: log automatically as you go (near-zero cost), write up only if there's room in the report.**

## Explicitly not doing

- Full live A/B deployment of the tool inside a real company's CI process — good idea, wrong project size.
- Large-scale interview study (10+ interviews) — the 2-4 think-aloud sessions above capture the same value at a fraction of the cost.

- **Scale discipline.** Tier 1, 2, and parts of Tier 3 don't need Suzanne's sign-off to start — they're pure engineering and can begin whenever the relevant tool component is ready. Tiers 5 and 6 add texture and, if the PR attempt lands, a genuinely rare piece of external validation for an MSc dissertation.

This still fits inside Weeks 5–6.5 without changing your build timeline — Tiers 1 and 2 run alongside normal development, and only Tier 4 (the expensive part) needs the evaluator-recruitment lead time already scheduled for Week 5.
