This document expands it into a fuller method set, because the Evaluation/Reflection section of the report is worth 20% of your grade — the same weight as Methodology — and it's also where your actual research contribution lives (per the hybrid dev/research framing already agreed with Suzanne).

This still exceeds the state of practice — `terraform-docs`, the industry-standard tool in this documentation-generation space, has no human comprehension evaluation at all; its accuracy claim is purely architectural (documentation is derived deterministically from source, and CI enforcement keeps it in sync). A rigorous self-conducted evaluation, done honestly, is already ahead of that bar. Hu et al. (2022)'s finding that human judgment beats automated metrics for documentation quality doesn't disappear because recruitment does — see "Threats to validity" below for how that tension is handled rather than ignored.

Methods below are grouped by cost, so you can see at a glance what's cheap and what needs more setup.

## Tier 1 — Automated / programmatic checks (no humans, no recruitment, run continuously)

These are no longer a cheap warm-up ahead of a "real" recruited study — with recruitment off the table entirely, Tiers 1–4 together *are* the evaluation. They cost nothing in evaluator time (there are no evaluators) and can run from Week 1 onward as regression checks, not just in dedicated evaluation weeks.

### 1. Golden-file regression testing
Commit the expected `.md` output for all 10 fixture pipelines to the repo. Regenerate them on every CI run (already wired via `tool1/single_pipeline.py`'s `--check` flag, Phase 4) and diff against the committed copy — any drift fails the build. This is the same regression mechanism `terraform-docs` (the industry-standard Terraform documentation generator, already cited as prior art in `BUILD_PLAN.md` Phase 4/6) and HashiCorp's `terraform-equivalence-testing` use: neither tool relies on human review to catch documentation drift — both rely on a deterministic diff against a checked-in expected output.

This is deliberately more rigorous than it sounds. `terraform-docs` doesn't run a human-comprehension evaluation at all — its accuracy claim is purely architectural (docs are derived deterministically from source, and CI enforcement keeps them in sync). Golden-file testing is exactly that architectural guarantee, made explicit and automated for this project. It largely subsumes the determinism/variance check below for the non-LLM layers (Phase 3/4 output is already provably deterministic — a golden-file mismatch there is a bug, not expected variance), and becomes the actual mechanism for measuring LLM output drift once Phase 5's beautification layer lands (a golden file for the LLM layer records one accepted "known-good" output per pipeline; failing the diff doesn't necessarily mean a regression the way it does pre-LLM, but it flags every change for deliberate review rather than letting drift pass silently).

### 2. Coverage check
Does every job, trigger, and secret present in the IR actually appear somewhere in the generated documentation? Since you control the IR, this is a straightforward scan: for each IR field, check it's referenced in the output text. Gives you a hard completeness number, not just a subjective "felt complete" rating.

### 3. Diagram-structure check
Does the Mermaid graph's nodes and edges match the IR's job dependency graph exactly? Automatable via graph comparison (build the expected graph from the IR, parse the generated Mermaid, diff them). Validates Tool 2's "unified diagram" claim without needing a human to eyeball it.

### 4. Determinism / variance check
Run the same pipeline through the LLM layer multiple times (and at different temperature settings) once Phase 5 lands. Measure how much the natural-language output varies while the underlying facts stay fixed. For the non-LLM layers (Phases 3–4), this is now redundant with golden-file testing above — deterministic Python code either matches its golden file or has a real bug, there's no "variance" to measure there. This method's remaining scope is specifically the LLM layer, where golden-file testing catches *that* something changed but this method characterizes *how much* it changed and whether it stays within an acceptable band.

### 5. Readability metrics
Flesch-Kincaid or similar, computed on the generated text. Not a replacement for human judgment on clarity (that's Hu et al.'s whole point, and still holds), but a free secondary signal that costs nothing to add.

**Recommendation: include all five.** They strengthen Methodology and Evaluation sections without touching evaluator recruitment.

## Tier 2 — Robustness / stress testing

### 6. Error injection
Deliberately break test pipelines — a dangling dependency, a malformed `if` condition, an undefined secret reference. Does the tool flag the problem, or silently produce plausible-but-wrong documentation? This is exactly the kind of stress test examiners want to see in a critical reflection, and it's a direct test of hallucination risk in the LLM layer.

**Recommendation: include.** Cheap to build (you already have working pipelines to mutate), and it's a strong, specific data point for the Reflection section.

## Tier 3 — Comparative / correctness methods (uses real repos, moderate setup cost)

### 7. Correctness check (already in original plan)
Trigger real pipelines on 4-5 real repos, compare GitHub's actual job/status output against what the tool documented. Validates the parsing + IR layer specifically.

### 8. Natural-pairs comparison (upgrade to "vs. human-written docs")
Instead of asking recruited people to write fresh documentation for the study, find repos that **already have** human-written pipeline documentation — READMEs, CONTRIBUTING.md, wiki pages describing the CI setup — and compare the tool's output against those directly.

This removes a recruitment dependency (nobody has to write anything new) and gives you documentation that's "real" — written for actual developers, not written for the purpose of your study. Directly satisfies the brief's "comparing... with documentation written by human developers" requirement.

**Recommendation: use this as the primary human-comparison method**, replacing "ask evaluators to write docs" with "find docs that already exist." Zero recruitment risk, more authentic baseline.

## Tier 4 — Self-conducted rigorous checks (no recruitment; objective, pre-registered, bias-mitigated)

Recruiting developer evaluators is off the table for this project (Supervisor guidance). The two methods below replace the previously-planned recruited study, redesigned so a single author's judgment stays defensible: every score comes from a checklist prepared *before* looking at any tool output, every rated fact is objectively checkable (present/missing/false), and no method here asks the author to rate subjective qualities like "clarity" on a Likert scale — a sole rater scoring their own tool's output on taste is not evidence.

### 9. Pre-registered fact-checklist protocol (Tool 1)
Same three conditions as the original blind three-way comparison, because they still directly test the architecture's central claim (Python-extraction-then-LLM beats "just ask an LLM to read the YAML"):
1. Plain structured text (Layer 3a, no LLM)
2. Full tool output (structured text → LLM-polished)
3. Naive baseline — raw YAML dumped straight into an LLM with an "explain this" prompt

What changes is what gets scored. Before generating any of the three outputs for an evaluation pipeline:
- Enumerate every objectively checkable fact in that pipeline's YAML — trigger X exists, job A needs job B, secret S is required, condition C gates job D, and so on.
- Commit this checklist to the repo. The commit timestamp is the evidence it was pre-registered, not retrofitted after seeing what each condition got right or wrong.

Then, for each of the three outputs, score against the checklist:
- Facts correctly present
- Facts missing
- Facts stated that are false (**hallucination count**)

The hallucination count is the headline metric. It's exactly where the naive raw-YAML baseline is expected to lose — an LLM asked to "explain this" YAML with no structural guarantees is free to invent plausible-sounding but wrong claims about trigger conditions, dependency order, or secret scope, in a way neither of the other two conditions can (condition 1 has no LLM at all; condition 2's LLM only rewrites already-extracted facts, per the Phase 5 prompt design). Unlike a 1–5 clarity rating, "this document claims a fact that is false" is checkable by anyone re-reading the same YAML, including an examiner.

**Bias mitigations** (necessary because the author is also the tool's builder and the sole rater):
- Score fact-by-fact, not document-by-document — reduces the halo effect of an otherwise-fluent document getting the benefit of the doubt on a specific claim.
- Randomise the order the three conditions are scored in, per pipeline.
- Strip identifying formatting from the three outputs before scoring, where practical (condition 2's tool output is visually distinctive — Mermaid fences, the "JOBS (in order)" heading style — so full blinding isn't achievable here the way a recruited-evaluator blind study could manage; noted honestly as a limitation in "Threats to validity" rather than claimed as full blinding).

### 10. Answerability audit (Tool 2)
Split-group comprehension testing is impossible with one person — there's no second group to hold out the raw YAML for. Replacing it with a method that's still objective and still tests comprehension outcomes, not stated preference:
- Write concrete questions with ground-truth answers derived directly from the YAML: *"If I push to main, what runs?"*, *"Which pipeline fires on a PR to the release branch?"*, and similar.
- For each question, check — binary, objective — whether it's answerable from the tool's unified doc alone, without consulting the raw YAML.
- Report the **answerability rate** (questions answerable / total questions) as the headline number.

Self-timing how long it takes to answer from the doc vs. from raw YAML may be included as anecdotal texture in the report, clearly labelled as a single author's informal timing, not a controlled measurement — never presented as a headline result or as if it carries the statistical weight a real split-group timing study would.

**Recommendation: run both.** These, together with Tiers 1–3, are the complete evaluation for this project.

## Threats to validity — single-author evaluation

This is not a disclaimer tacked on at the end; it's part of the methodology and belongs in the report's Evaluation/Reflection section, not just here.

**The core threat:** the author is not a neutral rater. Every fact-checklist score, every answerability judgment, and every hallucination count in Tier 4 is produced by the same person who built the tool being evaluated. That is a real threat to validity, not a technicality — a recruited-evaluator study exists specifically to remove this dependency, and this project cannot run one.

**Mitigations actually in place:**
- **Pre-registration.** The fact checklist for each evaluation pipeline is committed to the repo, with its own commit timestamp, before any of the three conditions' outputs are generated. This forecloses the most obvious failure mode — quietly deciding what counts as a "fact" after seeing which tool got it right.
- **Objective, fact-level checks instead of subjective ratings.** Nothing in the redesigned Tier 4 asks the author to rate clarity, usefulness, or quality on a 1–5 scale. Every score is "is this specific, YAML-derived fact present / missing / falsely stated" — a checkable claim, not a preference.
- **Randomised scoring order and fact-by-fact scoring**, reducing (not eliminating) halo-effect bias toward whichever condition happens to read more fluently.

**What isn't mitigated, and is acknowledged rather than hidden:** full blinding isn't achievable (the tool's own formatting is recognisable), and no amount of pre-registration replaces an independent rater's judgment on the things that are genuinely subjective — is this phrasing actually clearer to a developer who didn't write the tool? Hu et al. (2022)'s finding that human judgment outperforms automated metrics for documentation quality doesn't stop being true because recruitment is off the table. This plan respects it by *confining* author judgment strictly to objectively checkable claims (a fact is present, missing, or false) rather than by pretending a self-administered clarity rating is an adequate substitute for the human-judgment signal Hu et al. actually studied. The gap between "objectively checkable facts, self-scored" and "perceived quality, independently rated by real developers" is real and is not closed by this evaluation — it's named here so the report can be honest about exactly what claim the evidence supports.

**This is future work, not an impossibility.** A recruited human study was descoped for this project's timeline and supervision constraints, not because it's infeasible in principle: Suzanne has already offered to help source student evaluators, and a post-completion opinion pass (showing the finished tool to a handful of developers after submission, outside the graded evaluation) remains an open possibility. Both are explicitly out of scope for this project's evaluation as submitted, and the report should say so in exactly those terms — a named future-work item with a concrete offer already on the table, not a hand-wave.

At a glance, the finalized evaluation method set spans five tiers, from fully automated checks that cost nothing to a stretch goal that depends on strangers on the internet:

|---|---|---|---|
| 1 | Golden-file regression testing | Free, automated (CI) | **Include** |
| 1 | Coverage check | Free, automated | **Include** |
| 1 | Diagram-structure check | Free, automated | **Include** |
| 1 | Determinism/variance check (LLM layer, Phase 5+) | Free, automated | **Include** |

| 2 | Error injection | Low, one-time build | **Include** |
| 3 | Correctness check (real pipeline runs) | Moderate | **Include** (already planned) |
| 3 | Natural-pairs comparison | Moderate | **Include** (upgrades the original plan) |
| 4 | Pre-registered fact-checklist protocol (Tool 1) | Moderate, self-conducted | **Include** — core method |
| 4 | Answerability audit (Tool 2) | Moderate, self-conducted | **Include** — core method |
| 5 | Real PR submission | Uncertain, external dependency | Attempt early, report honestly either way |
| 5 | Practical/systems metrics | Free to log | Log always, write up if room |

**The shape of the argument this produces:** Tier 1 proves the tool is *reliable and honest* — golden-file regression testing and the coverage/diagram-structure/determinism/readability checks together mean nothing drifts, nothing is silently dropped, and nothing hallucinates without being caught mechanically. Tier 2 proves it fails safely under stress. Tier 3 proves it's *correct* against real-world ground truth and against documentation real developers actually wrote. Tier 4 is the closest a zero-recruitment project can honestly get to *actually useful to a human* — not by asking a human panel to rate it, which recruitment being off the table rules out, but by pre-registering exactly what "correct" means before generating output and then checking that objectively, fact by fact, with the hallucination count and answerability rate as headline numbers. Tier 5 adds a stretch: if the real-PR attempt lands a maintainer response, that's a genuinely rare piece of external validation most MSc dissertations don't get, self-conducted or not.

This is a smaller evaluation than a recruited study would have produced, and "Threats to validity" above says so plainly rather than dressing it up. It is not, however, a weaker one than the state of practice: `terraform-docs` ships with no human evaluation at all and relies purely on the golden-file-style regression guarantee Tier 1 already implements here. Everything in Tier 4 goes further than that baseline while staying honest about what one author's judgment can and can't establish.

With recruitment removed entirely, nothing here has an external lead-time dependency — Tiers 1 and 2 already run alongside normal development from Phase 3/4 onward, and Tier 4's fact-checklist/answerability work can start the moment Tool 1/2 output exists, without waiting on anyone else's calendar.
